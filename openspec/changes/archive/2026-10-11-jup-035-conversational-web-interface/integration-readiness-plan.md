## SSE, framing y productor

HTTP `text/event-stream; charset=utf-8`, no-store, proxy sin buffering cuando compatible. UTF-8 incremental estricto; framing soporta CR/LF/CRLF, BOM inicial, comentarios y múltiples data lines upstream; EOF sin evento delimitado no confirma nada. Envelope propio≤64 KiB, delta texto≤8 KiB antes escaping, cola lector≤64 frames y 1 MiB. Snapshot provisional answer≤4000 codepoints; **screen_snapshot completo no va en frame**. Input screen 1 MiB/body 2 MiB, resultado raw 1 MiB, frame del gateway 8 MiB y profundidad 32 propuestos; medir bytes antes de parse/alloc. Límites no truncan respuestas válidas; error explícito.

Eventos wirev2: `started` operación, sin anunciar intento; `waiting` motivo/saldos/límite automático; `attempt_started` claim confirmado con attempt_id/número/seq 0/deadline y resetbuffer; `snapshot` provisional del attempt actual; `delta` seq+offset UTF-16; `retry_scheduled` cierra provisional y fecha/reintentos restantes; `paused` razón/saldos/fecha mínima; `final` respuesta completa pequeña+IDs/result/context/evidence URLs+usage saneado **tras commit pareja**; `terminal` cancelled/failed y motivo/partial claramente incompleto. Eventos con intento usan ID `<operation_id>:<attempt_id>:<seq>`; eventos operacionales sin claim usan `<operation_id>:operation:<revision>`, sin inventar attempt_id/deadline. Comprobar scope/op/revisión y, cuando proceda, attempt/seq antes de append. Próximo intento buffer vacío; no unir fragmentos. No replay Last-Event-ID durable ni secuencia global idéntica tras crash; solo snapshot RAM o estado DB.

Proyección `wait_info` cerrada definida en [presupuestos acumulados](history-persistence-design.md#dos-presupuestos-acumulados-de-espera-por-solicitud); UI conserva pregunta, Stop, razón y ambos restantes durante espera/pausa. Dos presupuestos disjuntos de 120 s por operación, sin renovación en retry/resume ni cobro de pausa humana; hasta 240 s de espera automática, no deadline total. Reintentos de transporte/polling no crean otra operación ni restauran saldo. Control privado no se serializa.

Lector lento pierde suscripción, no productor. Heartbeatbackend 10 s/lector 25 s implican reconsulta, no Stop/retry. UI puede ver attempt_count con parciales separados; los incompletos no forman mensajes completos/contexto. Recursos GET conservan resultados/captura/evidencia íntegros; GET temporal fallido después completed muestra detalles pendientes y reintenta lectura, nunca modelo.

Backend registry por scope+operation+attempt; productor supervisado independiente de StreamingResponse/componente. No BackgroundTasks cuya vida dependa de cerrar response. Pool de red 8 y controles/auth/Stop 4 separado; SQL de conexiones cortas, no transacción durante red. Resumen comparte techo 8 del processor, máximo 1/solo plazas ociosas; deja capacidad para≥5 chats. Scheduler de operaciones waiting/expired distinto de tarea resumen RAM; ver [plazos/fencing](history-persistence-design.md#cuatro-intentos-y-plazos).

Adaptador processor chat usa una llamada stream=true `/v1/chat/completions`, roles reales, schema canónico, alias/pin existentes, **retries de HTTP/gateway/router 0**; solo backend hace 3 adicionales. No fallback de modelo/tool loop/repair JSON/calentar caché. Extraer provisional solo string answer por parser JSON incremental con escapes/surrogates/keys duplicadas; no regex ni mostrar reasoning/schema entero. Candidato final FinOps completo va por chunks internos UTF-8≤8 KiB, offset de bytes/total/hash y candidate_end; no partir codepoints ni mezclar attempt. Backend valida ensamblado/schema/refs/cifras antes de CAS final.

stop/[DONE]/EOF no bastan para completed. finish_reason length/truncamiento transitorio según política max 4/output 800; JSON completo inválido/guard violado permanente. Usage reportado una vez por intento; ausente/conflictivo=unknown, no 0 ni suma duplicados. Guardar modelo/proveedor observados cuando existan; no derivarlos de alias. Retry-After/error_type/provider_code/status solo allowlist, sin cuerpos/headers raw.

Tiempo aprobado120 s por intento/max4/480 activos. **Retirar upstream total30 s e idle20 s para la respuesta principal**; aplicar [presupuesto efectivo](history-persistence-design.md#presupuesto-http-efectivo-dentro-del-intento): margen final5 s propuesto y HTTP `max(0,deadline−ahora−5s)`, sin restart del reloj. Preparación específica≤10 s y DNS/conexión≤5 s dentro del restante, nunca añadidos. Primer token/pausa de lectura tienen el presupuesto HTTP restante, sin otro corte20/30 s; heartbeat no amplía deadline. Resumen background conserva su propuesta separada30 s por lote, sin arrastrarla al principal.

Recomendación de configuración futura: namespace chat en processor admite restante≤120 s sin cambiar la restricción del cliente de ingesta; petición gateway solo server con `timeout` dinámico. La documentación [LiteLLM timeouts](https://docs.litellm.ai/docs/proxy/timeout) admite per-request timeout y diferencia timeout completo de stream_timeout de primer chunk. El override/techo de primer chunk del chat deben permitir el mismo restante, mientras embedding/ingesta conservan30 s; no subir global request_timeout a120 por arrastre, cambiar alias/proveedor o habilitar retry/fallback. ## Canal interno privado, autenticación y fencing

HTTP privado en UN DockerServer aprobado PM 21:17:13; HTTPSbrowser/backend externo. Red dedicada no reemplaza autenticación. Proponer HMAC-SHA256 con secret exclusivo≥32 bytes, readonlyfile y redactor SecretStr, nunca JWT/Azure/master/health/virtual key/diagnóstico. No credential nueva creada ahora.

Rutas privadas: GET `/internal/chat/v2/descriptor` autenticado con nonce y respuesta firmada de boot/hash/versions/capacidad; POST `/internal/chat/v2/attempts` con scope/op/attempt/número/contexto/versión/deadline/capability/target_boot; POST `/internal/chat/v2/attempts/{id}/cancel`; POST `/internal/chat/v2/summaries` no streaming, solo QA+schema summary+scope control. Scope/metadata de control del resumen no entran messages al LLM. No exponerlas en app health 8001 ni browser.

Headers X-Chat-Key-Id/Time/Nonce/Signature. Firma sobre method/path/time/nonce exactos/SHA256 bodybytes y prefijo chat-v2; key-id en allowlist, compare_digest, desfase≤30 s y nonce UUID consumido atómicamente antes await. TTL 180 s/capacidad 4096; lleno 503 sin expulsar nonces vivos. Descriptor respuesta incluye nonce de solicitud/status/hash del body firmado. No logs de firmas/capabilities/payload; no normalizar cuerpo diferente después de verificar.

Processor lee parametrizado chat_operations JOINconversation y exige tenant+user+conversation+operation **current_attempt_id/número**, active/deadline/boot/capability antes de inferir. Capability no autoriza otra operación. Claim RAM se consume una vez por `(boot,attempt_id)`; retain hasta deadline+30 s, nunca evict running para meter otro. Reinicio cambia boot, no vuelve a aceptar claim anterior aunque firma/nonce nuevos. Backend consume intento incierto y espera viejo deadline antes de claim siguiente. Callback viejo se rechaza por fence; abort no garantiza que provider deje de cobrar.

Cancel firmado repite scope/control y cierre best effort; backend único dueño de CAS terminal. Durante streaming verificar estado cada lote/almenos 500 ms; lectura DB insegura/no disponible suspende salida y cierra. Solicitud de resumen valida propietario/fuentes/hash/revisión y read-only scope, con request_id consumido en RAM/boot y no retry tras crash; solo backend instala artefacto CAS. No compartir tabla/resumen entre usuarios, ni confiar en authorized_scope sin autenticar/consultar.
